ASSISTANT:
I've written the security spec for session 05 and committed it to `main` (`docs/modules/security/spec.md`, marked draft until you approve it). There's no remote, so nothing was pushed.

**What it covers:** 10 rules, SECURITY-S01 to S10:
- **Access:** HTTP Basic login, passwords stored as BCrypt hashes. Only `DELETE /api/products/**` needs ADMIN; everything else is open.
- **401:** anonymous callers get 401 on DELETE, and wrong credentials get 401 on any endpoint, including open ones.
- **403:** a USER trying to DELETE gets 403. The role check runs before the product lookup, so a USER deleting id 999 or `abc` gets 403, not 404 or 400.
- **Sessions:** the API is stateless (no session cookie) and CSRF is off.
- **Other headers:** a `Bearer` token is ignored and the request counts as anonymous.

The spec also has a table of every endpoint against anonymous, `user`, `admin` and a wrong password, plus the edge cases EC-15 to EC-19.

**Your answers:**
1. **Paths outside `/api/products`:** permit all, so an unknown path gets the normal 404 error response.
2. **401/403 error text:** 401 is `Unauthorized` / `Authentication required` for both anonymous and wrong credentials. 403 is `Forbidden` / `Access Denied`, which matches the MCP example in FR-MCP-04.

**Decided without asking (veto any of these):**
- **Where the ADMIN rule lives:** a URL rule in Spring Security's request filters, not `@PreAuthorize`. This gives the "check role before lookup" behaviour without touching the product module.
- **Users:** hardcoded in `SecurityConfig` and not configurable through properties.
- **Login challenge header:** `WWW-Authenticate: Basic realm="Realm"` (Spring's default).
- **Security response headers:** Spring Security's defaults stay on and aren't tested.
- **Existing product tests:** PRODUCT-T04, T10, T11 and T36 call DELETE. They will send `admin/admin123`, and their expected results stay the same.
- **Username case:** usernames match regardless of case and passwords are case-sensitive (Spring's default). Not tested.
