# mcp-server: Specification
Status: approved (session 09, 2026-11-25)
Implements: FR-MCP-01..07, NFR-01, NFR-02, NFR-06, EC-21, EC-22, AC-06, AC-07, AC-08

## 1. Responsibility

The `mcp-server` module is a separate Maven module, `product-mcp-server`. It is a Spring AI MCP server that uses the
stdio transport and exposes the five Product endpoints of `product-backend` as five MCP tools. It covers:

- the five tools: names, descriptions, parameter schemas, and how each one maps to one backend endpoint
- the HTTP client (`RestClient`) that calls the running backend, with its base URL and Basic credentials taken from
  configuration
- turning backend responses into tool results. Success returns product JSON (or a short text for delete). An error
  becomes an MCP tool error with the text `<status> <reason>: <detail>`.
- keeping stdout clean for the stdio protocol

It does **not** validate product input or enforce security. Both stay in `product-backend`, which is the single
source of truth (PRODUCT-S10..S12, SECURITY-S01..S10). The MCP server passes the AI's input through and reports
whatever the backend answers. It has no database and no state of its own, and it doesn't start or manage the backend.

## 2. Public interface

`product-backend`. Package: `com.aieng.productmcpserver`.

**What's in it:** 43 tests, `MCP-SERVER-T01` to `T43`. Every spec rule S01–S16 has at least one test, and the coverage tables also map the edge cases, acceptance criteria and FR-MCP requirements.

**Your answer (Q1):** three test layers.
- **Layer 1, HTTP client (T01–T17):** `ProductApiClient` against `MockRestServiceServer`. These check the exact URLs and bodies sent, when the Basic header is sent, the trailing slash, how errors become text (sorted field errors, the fallback when there's no `detail`), unreachable and timeout, and that credentials never leak.
- **Layer 2, MCP tools in the same JVM (T18–T36):** these call the tools and get real `CallToolResult`s back. They check the 5 tool names, descriptions and schemas exactly, the exact result JSON, `isError` on errors, `id is required` with no HTTP call, error-then-success, the non-web context and the config defaults.
- **Layer 3, stdio process (T37–T41):** starts the server as a child process against a stub backend, sends `initialize`, `tools/list` and `tools/call`, and checks that every stdout line is JSON-RPC and that the log file is written.
- **Manual (T42, T43):** AC-07 and AC-08 in Claude Code against the real backend.

**Decided without asking (veto any of these):**
- The child process starts from the test classpath, not the jar, because `mvnw test` runs before the jar is built.
- Layer 3 reads raw JSON-RPC lines instead of using the MCP SDK client, so any stray stdout line fails the test.
- T16 tests the 10 s read timeout for real, so it adds about 10 s to the build. The 5 s connect timeout isn't tested on its own, because reliably forcing a connect timeout isn't practical in a test.
- At the tool layer, the price in the request body is checked by value, not exact JSON, because converting tool arguments may drop trailing zeros. Layer 1 checks the exact JSON, e.g. `1599.00`.
- The "unexpected error" case is triggered by a 200 response whose body isn't JSON.
- T36 checks the default config and is skipped if any `PRODUCT_API_*` env var is set on your machine.
- Test methods are named `T<NN>_…`, and stub response bodies are inline constants rather than fixture files.
