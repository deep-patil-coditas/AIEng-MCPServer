# mcp-server: Specification
Status: approved (session 09, 2026-11-25)
Implements: FR-MCP-01..07, NFR-01, NFR-02, NFR-06, EC-21, EC-22, AC-06, AC-07, AC-08

## 1. Responsibility

The `mcp-server` module is a separate Maven module, `product-mcp-server`. It is a Spring AI MCP server that uses the
stdio transport and exposes the five Product endpoints of `product-backend` as five MCP tools. It covers:

- the five tools: names, descriptions, parameter schemas, and how each one maps to one backend endpoint
- the HTTP client (`RestClient`) that calls the running backend, with its base URL and Basic credentials taken from
  configuration
- turning backend responses into tool results. Success returns product JSON (or a short text for delete). An error
  becomes an MCP tool error with the text `<status> <reason>: <detail>`.
- keeping stdout clean for the stdio protocol

It does **not** validate product input or enforce security. Both stay in `product-backend`, which is the single
source of truth (PRODUCT-S10..S12, SECURITY-S01..S10). The MCP server passes the AI's input through and reports
whatever the backend answers. It has no database and no state of its own, and it doesn't start or manage the backend.

The spec left two things for the plan to settle: which Spring AI version to use, and how a thrown exception becomes an `isError: true` tool result. I checked both with a throwaway build against the real libraries in the scratchpad. It isn't committed, and the plan marks what it showed as *(probe)*:
- **Version:** Spring AI **1.1.8** (MCP Java SDK 0.18.3). Spring AI 2.x needs Spring Boot 4, and CLAUDE.md fixes Boot 3.5.x. 1.1.8 works with Boot 3.5.16.
- **Problem found:** by default Spring AI wraps a returned `String` in JSON quotes. `delete_product` would return `"Product 3 deleted"` with quotes, and product JSON would be encoded twice. The plan adds a small `RawTextResultConverter` on every tool to return the text unchanged.
- **Errors:** an exception thrown from a tool comes back as `isError: true`, with the exception message as its only text. So `ProductApiException` messages reach the AI client exactly as the spec wants. A missing `id` reaches the method as `null`, so the `id is required` check works.
- **Tool tests:** calling a tool directly in a test needs a real `McpSyncServerExchange`. Passing `null` makes every call fail with empty text, so the test helper builds a real one.

**Steps in the plan:**
1. Add the module with the five tools fully declared (names, descriptions, parameters) but no behaviour yet.
2. Write tests T01–T41; only the catalogue, context and initialize tests should pass at this point.
3. Implement `ProductApiClient`.
4. Implement `ProductTools`.
5. Run T42/T43 by hand in Claude Code against the running backend.

**Decided without asking (veto any):**
- **PL-01:** Spring AI 1.1.8, set in the new module's `pom.xml` only.
- **PL-02:** Spring AI's own exception handling produces the tool errors; no custom handler.
- **PL-03:** the plain-text result converter on all five tools.
- **PL-04:** the timeouts (5 s connect, 10 s read) live in one constant in a new `ProductApiConfig` class. The app and the timeout tests T15/T16 both use it, so the tests check the real values.
- **PL-05:** the module uses `spring-web` + `spring-boot-starter-json`, not `spring-boot-starter-web`, so there's no Tomcat in a stdio server.
- **PL-06:** in-JVM tool tests turn off the MCP server (`spring.ai.mcp.server.enabled=false`). Otherwise it would read stdin and write stdout, which Maven's test runner uses to talk to the test process.
- **PL-07:** error text is built in a separate `ErrorText` helper. The reason phrase comes from `HttpStatus`, because the JDK HTTP client doesn't return one.
- **PL-08:** `ProductApiConfig` is a new class next to the spec's `McpToolConfig`.
